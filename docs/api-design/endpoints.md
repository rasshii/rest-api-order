# エンドポイント

1 周目 (注文する・注文を確かめる) の API の URL とメソッド。ユースケース・コマンド・集約のメソッドとの対応と、操作の名前は operations.yaml に置く。

## 一覧

| メソッドとパス | 操作の名前 | 成功したとき | 失敗したとき |
| --- | --- | --- | --- |
| `POST /orders` | `placeOrder` | 201。`Location` に作った注文の URL (`/orders/{orderId}`)、本文に注文の表現 | 入力の誤り・登録されていない商品・在庫の不足は、どれも 400。本文の形は `problems.md` |
| `GET /orders/{orderId}` | `getOrder` | 200。本文に注文の表現 | その注文 ID の注文が無いと 404。本文の形は `problems.md` |

## リソース

| リソース | パス | 表すもの |
| --- | --- | --- |
| 注文のコレクション | `/orders` | 受け付けた注文の集まり。注文を作るときの送り先 |
| 注文 | `/orders/{orderId}` | 1 件の注文。`{orderId}` は注文 ID |

- 注文明細は、注文の表現に含める。注文明細だけを指す URL は作らない
- 商品は、注文明細の中で商品 ID で指す。商品の表現は埋め込まない
- 商品と在庫は、1 周目の API にリソースとして出さない。商品の API は 2 周目で足す

## 名前の決まり

1 周目の 2 つの操作に当てた決まり。標準のメソッドで表せない操作の形と、API の版の表し方は、後の周回で比べて決める。

- パスのセグメントは、小文字の英語にする。2 語以上なら `-` でつなぐ
- コレクションは複数形にする (`orders`)
- パスの変数の名前は、用語集の code にする (`orderId`)
- 標準のメソッドで表せる操作では、パスに動詞を入れない。何をするかはメソッドで表す
- 基底のパス (`/api` など) は付けない。1 周目は、API の版をパスに入れない

## 選ばなかった案

| 案 | 選ばなかった理由 |
| --- | --- |
| `POST /orders/place` のように、動詞をパスに入れる | 何をするかはメソッドで表し、パスは操作の対象を表す |
| `PUT /orders/{orderId}` で、クライアントが決めた注文 ID で作る | 注文 ID はサーバーが決める。新しいリソースの URL をサーバーが選ぶなら、PUT でなく POST を使う |
| 注文明細をサブリソース (`/orders/{orderId}/lines/{lineId}`) にする | 1 周目には注文明細を 1 つずつ扱う操作が無い。注文明細は注文と一緒に作り、作った後に変えない |
| 商品の表現を注文明細の中に埋め込む | 注文明細は、注文した時点の価格と税率を、単価と税率として写して持つ。商品の今の表現を埋め込むと、写した値と今の値が並ぶ |
