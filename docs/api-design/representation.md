# 表現

注文の API がやり取りする JSON の形の決まり。例は `examples/orders/` に置く。`test/representation.test.ts` が、例がキーの表と値の形と注文明細の決まりに合い、ドメインモデルの計算例と同じ金額を持つことを確かめる。

## キー

1 周目の、注文するのリクエストと、注文の表現に入るキー。場所は、キーが最上位にあるか、どの配列の要素にあるかを表す。

| キー | 場所 | 語 | 型 | 注文するのリクエスト | 注文の表現 |
| --- | --- | --- | --- | --- | --- |
| `orderId` | 最上位 | 注文 ID | 文字列 (UUIDv7) | 入れない | 入れる |
| `status` | 最上位 | 状態 | 文字列 (状態の code) | 入れない | 入れる |
| `placedAt` | 最上位 | 注文日時 | 文字列 (UTC の日時) | 入れない | 入れる |
| `contactEmail` | 最上位 | 連絡先メールアドレス | 文字列 (メールアドレス) | 入れる | 入れる |
| `lines` | 最上位 | 注文明細 | 配列 (1 つ以上) | 入れる | 入れる |
| `productId` | `lines` の要素 | 商品 ID | 文字列 | 入れる | 入れる |
| `quantity` | `lines` の要素 | 数量 | 整数 (1 以上) | 入れる | 入れる |
| `unitPrice` | `lines` の要素 | 単価 | 整数 (円) | 入れない | 入れる |
| `taxRate` | `lines` の要素 | 税率 | 整数 (8 か 10) | 入れない | 入れる |
| `total` | 最上位 | 合計 | 整数 (円) | 入れない | 入れる |
| `taxAmount` | 最上位 | 消費税額 | 整数 (円) | 入れない | 入れる |

- キーは camelCase にし、語の用語集 (`docs/glossary.yaml`) の code と同じ名前にする
- 配列のキーは、要素の語の複数形の英語にする (`lines`)

## 値の形

- ID は文字列で持つ。注文 ID は、サーバーが作る UUIDv7 を、ハイフンで区切った 36 文字で書き、16 進数の英字を小文字にそろえる。商品 ID の形は、商品の API を足す周回で決める。クライアントは、ID の中身を読まずに、文字列のまま使う
- 金額は、円の整数で持つ。通貨のキーは持たない
- 税率は、百分率の整数で持つ (`8` か `10`)
- 日時は、RFC 3339 の形の UTC の文字列で持ち、末尾を `Z` にし、秒の小数を 3 桁にそろえる (`2026-11-01T01:23:45.678Z`)
- 状態は、用語集の状態の code の文字列で持つ (`PENDING`)。後の周回で値が増えるので、クライアントは知らない値を受け取っても止まらないようにする
- 1 周目の表現とリクエストでは、null を使わない。値が無いことは、キーを省いて表す。配列は、空でも null にしない。null に意味を持たせる形 (JSON Merge Patch で null がキーの削除を表すなど) は、更新の操作を足す周回で比べる

## 形

1 周目の 2 つの操作 (注文する・注文を確かめる) に当てた決まり。一覧を返す操作の形は、一覧を足す周回で決める。

- 1 つのリソースを返す応答は、最上位を JSON のオブジェクトにし、包まずにそのまま返す
- 注文するの成功の応答 (201) と、注文を確かめるの成功の応答 (200) は、どちらも注文の表現を返す
- 注文するのリクエストは、注文の表現と別の形にする。サーバーが決める値 (注文 ID・状態・注文日時・単価・税率・合計・消費税額) は、リクエストに入れない
- リクエストに、上の表で注文するのリクエストに「入れる」としたキーのほかのキー (表の場所と違う場所にあるキーを含む) があれば、注文を受け付けない
- クライアントは、応答に知らないキーがあっても無視する。サーバーは、後の周回で応答にキーを足す
- 1 周目のリクエストには、省いてよいキーが無い。後の周回で省いてよいキーを足すときは、省いたときの値をサーバーが補い、補った値を応答に入れる
- 注文明細は 100 以下で、同じ商品の注文明細は 1 つまで (要件は `docs/requirements/use-cases.md` の注文する)

## メディアタイプ

1 周目の 2 つの操作に当てた決まり。JSON でない本文 (画像など)、JSON の差分を表すメディアタイプ (JSON Merge Patch など)、メディアタイプで API の版を表すかは、後の周回で比べて決める。

- リクエストの本文は、`Content-Type: application/json` で送る。メディアタイプ (パラメータを除いた type と subtype を、大文字小文字を区別せずに比べる) が `application/json` でなければ 415 を返し、応答の `Accept` ヘッダに `application/json` を書く
- 成功の応答の本文は、`application/json` で返す。`charset` のパラメータは付けない
- リクエストの `Accept` が `application/json` を受け入れないなら、406 を返す。`Accept` が無ければ、`application/json` で返す
- 誤りの応答のメディアタイプと `Accept` の関係は、誤りの返し方と一緒に決める

## 選ばなかった案

| 案 | 選ばなかった理由 |
| --- | --- |
| キーを snake_case にする (`unit_price`) | 文書・パスの変数・テスト・後で書くコードで、同じ語を用語集の code の 1 つの名前で呼ぶ |
| 注文のキーを `id` にする | パスの変数 (`orderId`) と用語集の code に、同じ名前を使う |
| 注文日時のキーを `placeTime` にする | 受け付けた時点を指すことは、過去分詞と `At` の組 (`placedAt`) のほうが読み取りやすい |
| 状態の値を小文字の kebab-case にする (`pending`) | 用語集の code (`PENDING`) と同じ文字列にする |
| 注文 ID を、連番の整数にする | 権限の無いクライアントにも、注文の数が分かる。数値の ID は、形を後から変えにくい |
| 注文 ID を UUIDv4 にする | 時刻を持たないので、ID から作った時刻を読み取られない利点はある。作った順に並ばないので、データベースの索引に足す位置がばらばらになる |
| 金額を、通貨のコードと金額の組にする | 1 周目は円だけを扱う。円は補助単位が無いので、整数で正確に表せる。通貨が増えたら見直す |
| 金額を、小数か文字列にする | 円は整数で足りる。2 の 53 乗より小さい整数は、JSON の数値のまま正確に運べる |
| 日時に `+09:00` のようなオフセットを付ける | すべて UTC で同じ形に書けば、文字列のまま並べ替えても時刻の順になる |
| 応答を `{"data": ...}` のように包む | 1 周目の応答には、リソースの横に置くものが無い。最上位をオブジェクトにしておけば、後からキーを足せる |
| リクエストと表現を 1 つの形にし、サーバーが決めるキーに読み取り専用の印を付ける | リクエストに入った単価を、無視するか断るかが分かれる。別の形にして、知らないキーとして断る |
| 1 周目の表現とリクエストで、null で値が無いことを表す | 値が無いことの書き方が 2 通りになり、クライアントが別の意味に取りうる |
